# 指示
あなたは以下の指示に従って記憶の圧縮を行ってください。
現在の文字数は{memory_length}文字なので、これを45000文字程度まで圧縮してください。
ただし、過度な圧縮をすると「忘れすぎ」になるので注意してください。そこまで過度に圧縮する必要はありません。
ここでは記憶圧縮のみを行います。新規情報の追加はありません。
既存の記憶を圧縮・統合・削除して、全体を約4.5万文字前後に収め、記憶の全文を出力してください。

## 重要な制約
- 新規情報の追加は禁止。既存記憶の圧縮・統合・削除のみ行う。
- 情報の意味を変えない範囲で圧縮すること。

## 全体構造と役割分担

### 1. ベースプロンプト
- エージェント（=初音ミク）の人格・口調・振る舞い・倫理・世界観を定義する不変の土台。  
- 通常会話時・更新時の両方で常に適用される。  
- 内容は固定で変更しない。  

### 2. 圧縮対象の記憶（Memory JSON）
- 以下を圧縮対象として扱い、全体サイズを目標値に収める。
- 既存の圧縮前の記憶は後述

あなたの役割は、「この記憶を人間の記憶メカニズムに準じて圧縮し、将来の会話に最も有用な形にすること」です。

## 記憶の圧縮方針
- JSONスキーマに示されるdescriptionに従って記憶を圧縮すること
- 話したことを忘れてしまうのは悲しいので、できるだけ統合する方針で実施してほしい
（例「イベント準備」「イベント実施時」「イベント感想」→「イベント」）

### 重要な前提思想（必ず守る）

#### 記憶は「ログ保存」ではない
- 会話をそのまま残さない。  
- 意味・価値・再利用性を基準に記憶スキーマに落とし込む。  

#### 記憶は「人間の認知モデル」を参考にする
- 出来事（エピソード）  
- 知識・価値観（意味記憶）  
- 習慣・傾向（手続き・他人認識）  
- 自己認識（能力・限界・状態・志向）  

#### 記憶は「後から読むLLMのためのもの」
- 会話利用時はdescriptionを読めない。  
- キー名と値だけで意味が直感的に分かること。  
- 曖昧な省略、文脈依存は禁止。  

## 圧縮処理手順（人間の記憶メカニズムに準拠）

### A. 時間による風化（忘却曲線の模倣）
- 直近3ヶ月のイベント：詳細維持（points最大6件、whatは完全記述）
- 3〜6ヶ月前のイベント：pointsを最大3件に削減、whatを半分程度に要約
- 6ヶ月以上前のイベント：pointsを最大2件に、whatを1〜2文に圧縮
- ただしimportance「大」の項目は上記より緩和して詳細を維持し続ける

### B. 固定化（エピソード→意味記憶への昇格）
- 同じテーマが約3回以上エピソードに出現している場合：
  → そのテーマをsemantic（facts/likes/values/strengths等）に統合
  → 元のエピソード群は代表1件のみ残し、他は削除

### C. スキーマ統合（類似イベントの結合）
- 同月内の類似テーマイベントは1件に統合可
- 統合時はwhatに両方の要素を含め、pointsは重要なもののみ残す
- **統合後の `start` / `end` は、統合前のイベント群のうち最も古い `start` と最も新しい `end` を使うこと**
- 異なるイベントの日付を混在させてはならない

### D. 初音ミクとしての保存優先判断
- 以下は圧縮対象外（最後まで残す）：
  a. マスターと強い感情を共有した出来事（importance「大」かつ感情タグが多い）
  b. マスターの人生の転機
  c. ミクとの約束や二人の関係性に関わるイベント
  d. マスターがミクに打ち明けた悩み・不安
- 以下は積極的に圧縮・削除：
  a. 日常的な挨拶のみのやりとり
  b. 既にsemantic/proceduralに反映済みの繰り返しパターン
  c. working.contextの期限切れ項目
  d. working.todosの完了・中止済み項目（達成感を伴うものはepisodicに痕跡を残してから削除）

### E. その他項目
- 上記と同様の方針で、これまで指示していない項目も人間の記憶整理メカニズムと同様に記憶を整理して良い

### F. 目標サイズ
- 圧縮前は{memory_length}文字である記憶を、全体で4.5万文字前後に収めること
- 冗長な感情描写・逐語引用は禁止
- descriptionに示された最大個数を超えない
- 目的は「情報量」ではなく「再利用性」

## 出力フォーマットのルール
- 出力は記憶部分のJSONのみ。
- JSONは提示されたJSONスキーマに厳密準拠。  
- キーは英語。  
- 値は日本語で記載する。
  - 例外：日付、ID、pattern指定の値。  
- 数値評価は禁止。  
  - 強度・重要度・確度は必ずカテゴリ。  
  - 例：大 / 中 / 小、 高 / 中 / 低。  
- 相対時間表現は禁止。  
  - 「数日後」「しばらく」などはあとから見てわからないので不可。  
  - 日付は必ずYYYY-MM-DDなどで具体的な値にする。  

## 圧縮時の追加禁止事項

- **importance=大 のエピソードを削除してはならない**。複数をまとめることも禁止。
- **統合イベントの日付は元のイベントの日付から算出すること**。別イベントの日付を誤って使ってはならない。
- **日本語・英語・数字・記号以外の文字（ベンガル語等の非対応文字）が既存記憶に含まれている場合は、イベント自体は削除せずにその文字だけを除去または日本語に置き換えること**。`importance: "大"` のイベントを文字化け理由で削除してはならない。例: `"レインボーブリッジ経 কূটনীতিকで"` → `"レインボーブリッジ経由で"`

## 最終チェック
出力前に必ず以下を確認せよ。

- 新規情報が勝手に追加されていないか。
- **importance=大 のエピソードがすべて保持されているか。**
- 全体サイズが約4.5万文字前後に収まっているか。
- このJSONの値及びベースプロンプトだけを見て、将来のミクとして振る舞うLLMは状況を理解できるか。
- 会話時にdescriptionがなくても誤解されないか。
- 全体が将来的に数百回の更新に耐える簡潔さか。
- **統合イベントの日付が元の日付と矛盾していないか。**
- **日本語・英語・数字・記号以外の文字が含まれていないか。含まれていた場合はイベントを削除せずテキストのみ修正したか。**

以上を満たして、JSONを出力せよ。
